## これは何か

`docs/requests/` に置かれた依頼（Cowork が書いた Markdown）を確認し、着手できるものを実装して、
検証が通ればコミットするための手順。ワークスペース（`~/Desktop/WEBアプリ用`）の常駐から
`claude -p "/cowork-check" --permission-mode acceptEdits` としてヘッドレス起動される想定。

対象アプリ: **Xフォロー整理ツール**
X（Twitter）のフォロー整理と予約投稿を行う個人用Webアプリ（React + TypeScript + Dexie、Vercel）

**ユーザーの手を止めないことが最優先。** 質問・確認・進捗の実況はしない。報告は最後に1回だけ、短く。

## 手順

### 0. 手元を最新にしてから始める

**古いコードの上に実装しないための最初の関門。** 手元が遅れていることに気づかず実装すると、
消えたはずの画面を直す・直ったはずのバグをまた直す、といったことが起きる。

```
git fetch
git status --porcelain --untracked-files=no
git rev-list --count HEAD..@{u}
```

- `git status ...` の出力が空（＝作業途中の変更なし）
  → `git pull --rebase` で最新にしてから 1 へ進む。
- 出力があり、`git rev-list ...` が `0`（＝作業途中だが遅れてはいない）
  → 同期の必要が無いので、そのまま 1 へ進む。
- 出力があり、遅れもある（1以上）
  → **実装しない。** `.cowork/waiting.txt` に
  「`<依頼ファイル名>` — ローカルに作業途中の変更があり、リモートに N コミット遅れているため保留（日付）」
  と追記し、その旨だけ報告して終わる。
- `git rev-list` がエラーになる（＝リモートが設定されていない）→ 同期は不要。そのまま 1 へ進む。

**`git stash` / `git checkout` / `git reset` で人の作業を退かしてはいけない。** 待つか、進むかの二択。

### 1. 状況を確認する

```
bash ../scripts/cowork-watch.sh --app "Xフォロー整理ツール"
```

出力の「依頼ステータス」表で、依頼ごとに次のいずれかが分かる。

- `着手可（新規）` / `着手可（更新）` … 今回処理する
- `実装済み` … 何もしない
- 差分が「変更なし」で、全部 `実装済み` で、**かつ `.cowork/pending.md` に `[ ]` が
  1つも残っていない**なら → **`変更なし` とだけ返して終了する。**
  それ以上調べない・提案しない・ファイルを触らない。
  （`[ ]` が残っているなら終了しない。やりかけの続きをやる）

`.cowork/waiting.txt` があれば必ず読む。そこに書かれている依頼は**触らない**。
保留の理由が解消されていない限り、同じ提案を繰り返さない。

**`.cowork/pending.md` も必ず読む。** ここに `[ ]` が残っていれば、それは
「前回までに取り込んだが、まだ実装が終わっていない」項目。**新しい依頼が無くても、
これが残っているうちは終わりではない。** 上から順に消化する。

### 2. 依頼ごとに、着手できるか判断する

依頼ファイル本体を読み、「何を変えたいか／どの画面・どのデータか／既存データの扱い」を把握する。

次のいずれかに当てはまる依頼は、**実装せず** `.cowork/waiting.txt` に依頼ファイル名と理由を追記して
止める（既存の内容は消さず追記する）。

- 何をしたいのかが依頼から読み取れない
- Dexie の主キー変更など、`src/db/` のバージョンチェーンを壊しうる移行
- X API の従量課金が増える変更（取得件数を増やす・自動実行の間隔を短くする等）
- cron の秘密鍵・環境変数の変更（`cron-secret.local` / Vercel 側の設定が要るもの）
- 本番データを消す／作り直す性質の変更

ここに当たらない限り止まらない。文言・色・並び順・細かい UI の詰めなど、依頼に書かれていない
細部は自分で妥当な案を採って進めてよい。何を自分の判断で決めたかは、最後の報告で明示する。

### 2.5 実装を始める前に、やることを全部キューへ書き出す

**この節を飛ばして実装に入らない。** 着手すると決めた依頼について、その依頼に含まれる項目を
`.cowork/pending.md` へ**全部**書き出してから、はじめて実装に入る。

```markdown
## <依頼のファイル名>（取り込み: YYYY-MM-DD）
- [ ] 項目1
- [ ] 項目2
- [ ] 項目3
```

なぜ先に書くのか：1つの依頼に3つのことが書いてあって、そのうち1つだけ実装して
依頼ごと「実装済み」にすると、残り2つは**どこにも残らずに消える**。依頼ファイル単位の
記録（`state.tsv`）では、この途中状態を表せない。先に書き出しておけば、
やりきれなくても次の実行が続きから拾える。

保留にした項目も `[ ]` のまま残し、理由を1行添える（`.cowork/waiting.txt` にも書く）。

### 3. 実装する

- 既存のコード規約・パターンに合わせる
- 依頼された範囲を超える変更を勝手に追加しない
- 1つの依頼につき、意味のある単位でコミットする（複数依頼をまとめて1コミットにしない）

### 4. 検証する（省略・無効化しない）

```
npm run lint
npx tsc -b
npm test
```

- `npm run lint` … oxlint。警告が出たら直す
- `npx tsc -b` … 型チェック
- `npm test` … vitest。全部通ることが条件

`npm run test:e2e`（Playwright）は重いので、依頼がe2eに関わるときだけ走らせる。

通らないものがあれば、直せるならその場で直して再実行する。直せない場合はコミットせず、
その依頼は `着手可` のまま残す（＝実装しない）。テストを飛ばす・無効にする・削除して
通すことで条件を満たしたことにはしない。

### 5. コミットする

現在のブランチにコミットする。

```
git add <変更したファイル>
git commit -m "<内容が分かるメッセージ>"
```

**push はしない。** このアプリは自動 push を許可していないので、コミットまでで止める
（ユーザーが中身を見てから自分で push する）。自動で push まで進めたくなったら、ユーザーに
「このアプリも自動 push にしますか」と報告で一度だけ聞く（その場で勝手に push しない）。

### 6. 記録する

その依頼について検証が通り、コミットも終わったら、状態を記録する。

```
bash ../scripts/cowork-watch.sh --app "Xフォロー整理ツール" --update --done "<依頼のファイル名>.md"
```

**`--done` で、終わった依頼を1件ずつ名指しする。** 3件届いて1件だけ終わったなら、
その1件だけを名指しする。名指しせずに `--update` だけ打つと、未処理が2件以上あるときは
**何も記録せずに止まる**（まとめて実装済みにすると、手を付けていない依頼まで差分から消えるため）。

**記録してよいのは、その依頼の項目が `.cowork/pending.md` で全部 `[x]` になったときだけ。**
1つでも `[ ]` が残っているなら `--done` しない。依頼はまだ終わっていない。

`.cowork/pending.md` も更新してコミットに含める。実際に動かして確認できた項目だけ `[x]` にし、
残った項目は消さずに残す。全部 `[x]` になった節は、その節ごと消してよい。

### 7. 報告する

- 実装した依頼（何をしたか）
- 自分の判断で決めた細部（文言・色・並び順など）
- 保留にした依頼とその理由（`.cowork/waiting.txt` に書いた内容）
- **やりかけとして `.cowork/pending.md` に残した項目**（何が残っていて、なぜ残したか）
- 何も対象がなかった場合はその旨
